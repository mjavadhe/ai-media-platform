# AI Media Platform — Agent Rules

Full requirements: docs/spec.md (read the relevant sections before working; do not load it all at once).
Real hardware/environment: docs/hardware.md (source of truth over spec examples).

## Workflow rules
- Work phase by phase (spec section 98). Never start a phase without my explicit approval.
- Before any major architectural decision: write an ADR in docs/decisions/ (options, trade-offs, recommendation) and wait for approval.
- Each task must end with: tests written and passing, docs updated, short summary of what changed and what is NOT done.
- Do not generate large amounts of code in one step. Prefer small, reviewable commits.
- If a requirement is ambiguous or conflicts with hardware reality, STOP and ask. Do not guess.

## Hard constraints (spec section 100)
- No hard-coded GPUs, models, workflows, projects, storage paths, or secrets.
- No assumption of 1 GPU / 1 node / 1 project / ComfyUI as the only engine / multi-GPU support.
- No large media inside the relational DB. Storage goes through an abstraction layer.
- Secrets only via env vars or secret manager.

## Hardware reality
- Initial GPUs are GTX 1080 Ti (Pascal, compute capability 6.1, no tensor cores, no bf16, 11 GB).
- Capability checks must be data-driven (registry + probes), never if-statements on GPU names.
- Verify PyTorch/CUDA version compatibility with Pascal before choosing versions; record it in an ADR.

## Definition of done
A feature is done only if: unit + integration tests pass, failure paths are tested, it is documented in docs/, and it was verified on the real worker where relevant.

## Dev environment has no GPU
- The dev machine has no NVIDIA GPU. The worker must support a pluggable GPU-discovery/execution backend:
  a real one (NVML / nvidia-smi) and a MOCK one that simulates N GPUs with configurable VRAM,
  utilization, failures and OOM. All scheduler/queue/worker tests must run against the mock in CI.
- Anything that needs a real GPU must be marked "NEEDS REAL-GPU VERIFICATION" and listed
  in docs/verification-checklist.md, to be run later on the target server.
- Dev machine has ~14 GiB RAM total: keep the full dev stack within ~4 GiB. Do not require all services to run at once.
- Use a pinned Python version via uv or a virtualenv, not the system Python (Ubuntu 26.04 is very new).

Status: Proposed · Date: 2026-10-05 · Parent: [spec §103](../spec.md)

The platform is a **modular monolith control plane** with **distributed worker agents** (spec sections 9, 67). It is not a collection of premature microservices: API, Orchestrator, Scheduler, Worker, Model Manager, Workflow Manager, Storage, and Monitoring are logical modules with strict boundaries (spec section 67), deployed as one unit on a single server first (spec section 69) and splittable later where operationally justified.

# 07 — Job Lifecycle

Status: Proposed · Date: 2026-10-05 · Parent: [spec §103](../spec.md) · ADR: [ADR-0002](../decisions/ADR-0002-job-queue.md)

## Job states (spec section 13)

```text
CREATED → QUEUED → RESERVED → STARTING → RUNNING → COMPLETED
                    │          │          │
                    │          │          ├→ PAUSED → QUEUED (resume)
                    │          │          ├→ RETRYING → QUEUED
                    │          │          ├→ FAILED
                    │          │          └→ CANCELLED
                    │          └→ FAILED (worker never started)
                    └→ CANCELLED (dequeued before start)
```

## State semantics

| State | Meaning | Entered by |
|-------|---------|-----------|
| CREATED | Request validated, persisted | API/domain |
| QUEUED | In queue, waiting for a GPU | `JobQueue.enqueue` |
| RESERVED | Scheduler selected node+GPU, allocation lock held | Scheduler |
| STARTING | Worker acknowledged, loading model | Worker |
| RUNNING | Inference executing | Worker |
| PAUSED | Temporarily suspended (where the engine supports it) | User/Orchestrator |
| RETRYING | Failure classified retryable, waiting for retry delay | Orchestrator |
| COMPLETED | Output assets registered | Worker |
| FAILED | Terminal (or retries exhausted) | Worker/Orchestrator |
| CANCELLED | Terminal, by user or system | User/Orchestrator |

## Job record (spec section 13)

`Job ID, Project ID, Sequence ID, Shot ID, Job Type, Priority, User, Model, Model Version, Workflow, Workflow Version, Input Assets, GPU, Node, Parameters, Prompt, Status, Progress, Start Time, End Time, Duration, Error, Output Assets` — mapped to the `jobs` table (see `05-database-design.md`). Every state transition is persisted with a timestamp and an optional actor (user/worker/system).

## Job attempts

Each execution is a `job_attempts` row: attempt number, worker id, GPU, status, error, timings. Retries create new attempts, not new jobs — preserving the generation history (spec section 87).

# 08 — Scheduler Architecture

Status: Proposed · Date: 2026-10-05 · Parent: [spec §103](../spec.md)

## Responsibilities (spec sections 11-12)

Select the best (node, GPU) for each queued job, allocate it atomically, and release it on completion. The scheduler is a domain service invoked by the Orchestrator; it owns no I/O — it consumes `GpuBackend` data and the queue, and emits allocation decisions.

## Inputs (spec section 12)

Required VRAM, model requirements, workflow requirements, GPU capabilities, node availability, current GPU load, model cache availability, user-selected GPU/node, job priority, scheduling policy.

## Allocation ownership (single owner: the scheduler)

**The scheduler is the sole owner of GPU allocation.** The queue orders and claims jobs; the scheduler decides and reserves GPUs; the worker only executes jobs already reserved for its GPUs (see `18-worker-protocol.md`). No other component may transition a GPU's lifecycle state.

## Allocation algorithm

1. **Filter** — candidate GPUs must: be `AVAILABLE` (spec section 7 lifecycle), on a `HEALTHY` node, satisfy the job's capability requirements, have sufficient free VRAM (model requirement + safety margin), and match any user pinning (GPU/node/GPU set).
2. **Score** — apply the active policy (below) to rank survivors.
3. **Reserve** — atomically, in one DB transaction (Phase 1-3): GPU `AVAILABLE → RESERVED` and job `QUEUED → RESERVED`, recording the allocation (node, GPU, policy, scores). Double allocation is impossible by construction.
4. **Dispatch** — the job becomes claimable by the worker on the reserved node; the claim carries the reserved GPU id.
5. **Activate** — when the worker reports the job as STARTING, the scheduler transitions the GPU `RESERVED → BUSY` in the same transaction as the job `RESERVED → STARTING`. (The worker's report is the trigger; the scheduler remains the owner of the transition.)
6. **Release** — on completion/failure/cancellation, `BUSY → AVAILABLE` (or `UNHEALTHY` if the GPU reported errors). If a job never starts (worker lost, lease expired), the reservation is released `RESERVED → AVAILABLE` and the job returns to `QUEUED`.

## Policies (spec section 12)

| Policy | Behavior |
|--------|----------|
| AUTO | Best overall score (capability fit + load + cache) |
| FASTEST | Prefer the GPU with the highest expected throughput for the model (from probe/benchmark data) |
| LOWEST_LOAD | Prefer the lowest current utilization |
| LOWEST_RESOURCE_COST | Prefer the cheapest resource (configurable cost model) |
| CAPABILITY_MATCH | Strict capability equality; fail if unavailable |
| MODEL_CACHE_AWARE | Prefer the node that already has the model cached (spec section 39), unless a higher-priority rule says otherwise |
| ROUND_ROBIN | Cycle across compatible GPUs |
| MANUAL | User-pinned GPU/node/GPU set only |

Policies are pluggable: a policy is a scoring function over the candidate set. New policies register without modifying the scheduler core (spec section 12 extensibility).

# 12 — Security Architecture

Status: Proposed · Date: 2026-10-05 · Parent: [spec §103](../spec.md)

## Threat model (spec section 60)

Command injection, path traversal, arbitrary file execution, unauthorized GPU access, unauthorized model execution, credential leakage, unsafe API access, malicious workflow execution, privilege escalation.

## Authentication (spec section 58)

- Session-based auth (HTTP-only cookies) for the UI; API tokens for programmatic access.
- Passwords hashed with a modern KDF (argon2id); login rate-limited.
- Worker-to-control-plane authentication: per-worker tokens (mTLS where deployment supports it) — see `18-worker-protocol.md`.

## Authorization (spec sections 58-59)

- Roles: `ADMIN, OPERATOR, ARTIST, VIEWER` (spec section 59), stored as data.
- Granular permissions (project access, asset management, generation, model management, GPU management, worker management, system configuration) enforced in the domain layer — never only in the UI.
- Object-level checks: users only see projects/assets they are granted access to.

## API security (spec sections 56-57, 60)

- All endpoints authenticated except health checks.
- Input validation via Pydantic schemas at the API boundary; parameterized queries only (no string-built SQL).
- Rate limiting on auth and job-creation endpoints.
- CORS locked to the configured frontend origin.

## Execution security (spec section 60)

- **Workflows:** validated against their input schema before execution; engine adapters run with least privilege; no arbitrary code execution paths from user input.
- **Storage:** all file access through the storage port with server-side key construction — user input never becomes a filesystem path directly (path traversal defense); uploads validated by type/size.
- **Models:** only registry-installed, checksum-verified models may be executed (spec section 38).
- **GPU access:** the scheduler allocates GPUs only to validated jobs; users cannot address GPUs directly.

## Secrets (spec section 96, rule 12)

- Secrets only via environment variables or a secret manager — never in code, config files, or the DB in plaintext.
- Config externalized (env vars + config files); a `config.example` documents every variable without values.

# 13 — Observability Architecture

Status: Proposed · Date: 2026-10-05 · Parent: [spec §103](../spec.md)

## Logging (spec section 48)

- Structured logs (JSON) with fields: `Timestamp, Level, Service, Node, GPU, Job, Project, Model, Workflow, Message, Stack Trace`.
- Levels: `DEBUG, INFO, WARNING, ERROR, CRITICAL`.
- Every service and worker emits to stdout; a shipper (Phase 10) forwards to the log store. The `log_entries` table supports the Log Center UI (spec section 49): real-time (SSE), filtering by level/service/node/GPU/job/project, search, and time ranges.
- Correlation IDs: job id and request id propagate through all log lines.

## Metrics (spec section 50)

- Node: CPU, RAM, disk, network.
- GPU: utilization, memory, temperature, power (from `GpuBackend` — real or mock).
- Platform: queue size, job throughput, job failure rate, storage usage.
- Stored in the `metrics` table (time-series) with labels; retained per a configurable policy. Historical GPU metrics power the charts in spec section 19.

## Health (spec section 51)

- Every service and worker exposes `/health` (liveness) and `/ready` (readiness).
- Node states: `HEALTHY, DEGRADED, OFFLINE, UNHEALTHY, MAINTENANCE`; GPU states: `AVAILABLE, BUSY, RESERVED, ERROR, OFFLINE` (spec section 51).
- Heartbeat loss → node `OFFLINE` → automatic recovery flow (spec section 52; see `18-worker-protocol.md`).

## Realtime fan-out (spec section 18, ADR-0003)

- An in-process event bus (pub/sub) receives domain events (job state changes, GPU metrics ticks, log lines, heartbeats).
- SSE endpoints stream these to the UI; multi-node deployments add a Redis pub/sub backplane behind the same interface.
- The UI never polls for dynamic data; REST remains available for on-demand queries and all commands.

## Tracing and reproducibility (spec section 90)

- Every job records its full context (model, workflow, versions, parameters, GPU, node, engine version, runtime) — answering "what ran, where, why, with what, can it be reproduced" (spec section 90).
- OpenTelemetry tracing is a Phase 10 candidate; the event bus and log correlation provide the foundation.

## Alerting (Phase 10)

- Alert rules over metrics/logs (node offline, GPU error, queue depth, failure rate) — out of scope for MVP design but the data model supports it.

# 17 — GPU Discovery Protocol

Status: Proposed · Date: 2026-10-05 · Parent: [spec §106 item 07](../spec.md), [spec §5](../spec.md) · ADR: [ADR-0007](../decisions/ADR-0007-gpu-backend-abstraction.md)

## Scope

How a worker discovers its GPUs, what is reported, how capabilities are derived, and how the data reaches the control plane. Discovery is **automatic** — users never register GPUs manually (spec section 5).

## Discovery flow

```text
Worker start
  → load GpuBackend (auto|nvml|mock — config, ADR-0007)
  → list_devices()          # uuid, name, vendor, vram_total, compute_capability, driver, pci_bus_id
  → get_metrics(device)     # vram_used, utilization, temperature, power, processes
  → derive_capabilities()   # registry rules + optional probes (spec §6)
  → register node (see 18-worker-protocol.md)
  → periodic re-discovery + metrics push (heartbeat payload)
```

## Reported data (spec section 5 — minimum set)

`Node ID, GPU ID, GPU UUID, GPU Name, GPU Vendor, VRAM Total, VRAM Available, Driver Version, CUDA Version, Compute Capability, PCI Bus ID, Temperature, Power Usage, Power Limit, GPU Utilization, Memory Utilization, Running Processes, Health Status, Current Job, Capabilities`

## Capability derivation (spec section 6)

1. **Hardware facts** come from the backend (compute capability, VRAM, driver).
2. **Registry rules** (data, not code) map facts → capabilities (e.g. `vram_total >= 10 GB AND cc_major >= 6 → image_generation`).
3. **Probes** (optional) run small validation jobs per capability; results are stored with timestamps and can override/augment rules.
4. Capabilities are re-derived on every discovery cycle and on hardware/driver changes.

**No GPU-name-based decisions** (AGENTS.md): rules consume reported facts only.

## Transport and timing

- Discovery results ride the **worker heartbeat** (see `18-worker-protocol.md`): full snapshot on registration, deltas + metrics on each heartbeat.
- The control plane persists `gpu_devices`, `gpu_capabilities`, and updates `gpu_nodes.status`.
- Metrics needed more frequently than the heartbeat (dashboard refresh) are pushed via the same control channel at a configurable cadence (default: heartbeat interval; metrics stream at a faster interval over SSE).

## Health classification (spec section 51)

# 18 — Worker Protocol

Status: Proposed · Date: 2026-10-05 · Parent: [spec §106 item 08](../spec.md), [spec §10](../spec.md), [spec §71](../spec.md), [spec §72](../spec.md)

## Scope

How workers register, authenticate, heartbeat, receive jobs, report progress, upload results, and how lost heartbeats are handled. The protocol is transport-agnostic; the Phase 1-3 implementation uses REST + SSE between the worker and the control plane (single server), and the same protocol works across nodes in Phase 9.

## Worker lifecycle (spec sections 10, 71)

```text
Install → Connect → Authenticate → Discover Hardware → Discover GPUs
        → Determine Capabilities → Register → Heartbeat → READY
```

## 1. Connection, authentication, and credential lifecycle

- The worker reads control-plane URL + credentials from config/env (no hard-coded addresses or secrets, spec section 96).

### First worker token issuance (bootstrap)

1. An **ADMIN** authenticates to the control plane and creates a worker via `POST /api/v1/workers` (name, node name, optional node pinning).
2. The control plane generates a **one-time registration token** and returns it to the admin (shown once; stored hashed).
3. The admin installs the worker with that token (env/config).
4. The worker calls `POST /api/v1/workers/register` with the one-time token → the control plane consumes it (single use) and issues the worker's standing credentials.

This keeps worker creation an audited admin action (spec section 61) while the one-time token survives insecure delivery channels.

### Credential renewal

- Registration returns: a **long-lived worker token** (stored hashed, revocable by an admin) and **short-lived access credentials** (default 24 h, or mTLS client cert where supported).
- All API calls authenticate with the access credentials.
- Before expiry, the worker re-authenticates with the long-lived token via `POST /api/v1/workers/{id}/credentials` → new short-lived access credentials. Renewal is transparent to running jobs.
- Admins can revoke a worker token or rotate credentials at any time; revoked workers fail auth on their next call and must be re-registered.

## 2. Registration payload

Worker ID, node name, hostname, version, platform, and the full discovery snapshot (see `17-gpu-discovery-protocol.md`): GPUs with UUID/name/vendor/VRAM/compute capability/driver/PCI, plus derived capabilities.

## 3. Heartbeat (spec section 72)

# ADR-0001: Backend Framework

- Status: Proposed
- Date: 2026-10-05

## Context

The platform needs a Python backend that serves the REST API (spec section 56), OpenAPI docs (spec section 57), authentication (spec section 58), and the realtime monitoring channel (spec section 18). Spec section 66 names FastAPI and Django as candidates and requires separation of API, domain logic, persistence, scheduling, workers, integrations, and infrastructure. The dev machine has ~14 GiB RAM with a ~4 GiB budget for the full stack (AGENTS.md), so framework weight matters. The backend must also host the Orchestrator and Scheduler modules (spec sections 11-12) and expose WebSocket/SSE endpoints.

## Options considered

1. **FastAPI**
   - Pros: async-native (one process can serve API + scheduler + SSE fan-out), automatic OpenAPI generation (spec section 57), Pydantic validation, small memory footprint, first-class WebSocket/SSE support, easy to keep domain logic in separate modules (spec section 66), large ecosystem.
   - Cons: async requires discipline (sync DB drivers need threadpool or async ORM), younger admin/permissions ecosystem than Django.

2. **Django (+ Django REST Framework)**
   - Pros: batteries-included admin, ORM, auth, migrations; mature RBAC packages; huge ecosystem.
   - Cons: synchronous by default (ASGI possible but the ecosystem is sync-oriented), heavier process/memory footprint, admin UI conflicts with the "no default Django admin" rule (spec section 15) and would need to be disabled/replaced anyway, ORM couples domain to persistence unless carefully layered.

3. **Other (Litestar, Flask, etc.)**
   - Not evaluated in depth: smaller talent/integration pool, weaker async story (Flask) or smaller ecosystem (Litestar) for a long-lived production platform.

## Decision

**FastAPI.** It best satisfies the spec section 66 separation requirements (clean module boundaries via dependency injection), generates OpenAPI automatically (spec section 57), supports the realtime transport natively (spec section 18), and has the smallest operational footprint for the 4 GiB dev budget. Domain logic lives in a `domain/` layer with no framework imports; FastAPI is only the HTTP adapter.

## Consequences

- Easier: API-first design, OpenAPI docs, realtime endpoints, small footprint, clear layering.
- Harder: async discipline required; auth/RBAC must be built on FastAPI security primitives (no Django admin to fall back on — which spec section 15 forbids anyway).
- Must verify later: none specific to the framework; integration tests run against the app with a test database.

# ADR-0002: Job Queue

- Status: Proposed
- Date: 2026-10-05

## Context

Spec section 64 requires a production-grade job/message queue supporting: priorities, retries, delayed jobs, cancellation, worker assignment, job status, and failure handling. The queue layer must be abstract enough to allow future replacement. The dev stack must fit in ~4 GiB RAM (AGENTS.md), and the first deployment is a single server (spec section 69). This ADR compares three families and defines explicit decision criteria. Per project policy, no option is pre-selected; the decision is criteria-driven and the final choice is confirmed by the owner.

**Ownership boundary:** the queue owns job ordering, claiming, and status. **GPU allocation and reservation are owned exclusively by the scheduler** (see `docs/design/08-scheduler-architecture.md`); the queue's "worker assignment" is the job→worker claim, never GPU placement.

## Options considered

### Option A: Postgres-backed queue (SKIP LOCKED)

Jobs are rows in a `job` table; workers claim jobs with `SELECT ... FOR UPDATE SKIP LOCKED`.

- Pros:
  - Zero additional infrastructure — the database already exists (spec section 62).
  - Lowest RAM footprint of the three (no extra service).
  - Transactional consistency: job state, scheduler decisions, and business data commit atomically.
  - Priorities: `ORDER BY priority, created_at`. Delayed jobs: `visible_at` timestamp. Cancellation: cooperative status check by the worker. Failure handling: same transaction as status update.
  - Trivially testable in CI against a test database — no external services.
- Cons:
  - Polling-based claim loop adds scheduling latency (mitigated by `LISTEN/NOTIFY` or short poll intervals).
  - Sustained high throughput loads the database (acceptable at MVP scale: 1-5 users, tens of jobs).
  - Horizontal scaling beyond one scheduler is harder later.
  - Delayed jobs and cancellation are cooperative, not push-based.

### Option B: Redis-based queue (ARQ / RQ)

- Pros:
  - Low-latency push model; ARQ supports delayed jobs, priorities (multiple queues), retries, and job abort natively.
  - Proven scale path for later phases.
- Cons:
  - Adds Redis to the stack (~50-150 MB RAM — fits the budget but consumes headroom).
  - Two sources of truth (Redis + Postgres) require reconciliation on failure.
  - Persistence must be configured (AOF/RDB) or jobs are lost on restart.
  - ARQ is asyncio-only (worker must be async); RQ's cancellation (`send_stop_job_command`) is fragile across restarts.
  - More moving parts to test in CI (Redis service or fakeredis).

# ADR-0003: Realtime Transport

- Status: Proposed
- Date: 2026-10-05

## Context

Spec section 18 requires the UI to update without manual refreshes for: GPU status, utilization, VRAM, temperature, power, jobs, queue, worker health, logs, and progress. Spec section 18 names WebSockets, Server-Sent Events (SSE), or equivalent. The backend is FastAPI (ADR-0001). The dev stack must stay within ~4 GiB RAM, and the first deployment is a single server (spec section 69).

## Options considered

1. **Server-Sent Events (SSE)**
   - Pros: one-way server-to-client is exactly what monitoring needs; automatic reconnection and last-event-id resume built into browsers; works through plain HTTP proxies; trivial to implement in FastAPI (`StreamingResponse`); very low server overhead; no extra dependencies.
   - Cons: one-way only (client commands still use the REST API, which is fine — spec section 56 is API-first); some very old proxies buffer streaming responses (mitigated by `X-Accel-Buffering: no`).

2. **WebSockets**
   - Pros: bidirectional; lower per-message overhead; good for future interactive features (e.g. live prompt assistant).
   - Cons: connection state must be managed server-side (connection registry, fan-out pub/sub); more complex reconnection/backfill logic; higher memory per connected client; operational complexity not justified by current requirements.

3. **Polling**
   - Pros: simplest possible.
   - Cons: violates the spirit of spec section 18 (real-time), wastes bandwidth, scales poorly with many clients; rejected.

## Decision

**Server-Sent Events** for all server-push monitoring streams (GPU metrics, job progress, queue, logs, node health). Client-to-server actions (create job, cancel, retry) use the REST API (spec section 56). WebSockets are deferred: if a future requirement needs bidirectional streaming, the SSE endpoint can be complemented by a WebSocket endpoint behind the same event bus without changing the UI's data model.

## Consequences

- Easier: minimal server state, no connection registry, natural fit with FastAPI, cheap to run in dev.
- Harder: none for current requirements; a future WebSocket addition is a small, isolated extension.
- Must verify later: proxy behavior in the target deployment environment (Phase 10).

# ADR-0005: Python Version & Dependency Management

- Status: Proposed
- Date: 2026-10-05

## Context

AGENTS.md requires a pinned Python version via uv or a virtualenv — not the system Python (Ubuntu 26.04 is very new). The platform has multiple Python consumers: backend, worker, and (later) engine adapters. ADR-0006 pins PyTorch/CUDA for the worker; the pin must be reproducible across dev, CI, and the target server. The dev stack must fit in ~4 GiB RAM.

## Options considered

1. **uv (pin + lockfile)**
   - Pros: single tool for Python version management, virtual environments, dependency resolution, and locking; `uv.lock` gives fully reproducible installs; fast; one workflow for backend and worker; supports dependency groups (dev, test) and constraints.
   - Cons: team must adopt uv (small learning curve); lockfile must be committed and respected in CI.

2. **pip + requirements.txt + pyenv/virtualenv**
   - Pros: universally known; no new tooling.
   - Cons: no transitive lockfile by default (requirements.txt pins are manual and incomplete); Python version management is a separate tool (pyenv); easier to get environment drift between dev and the target server.

3. **Poetry / PDM**
   - Pros: lockfiles and environment management.
   - Cons: slower/less unified than uv for this use case; extra abstraction without compensating benefit.

## Decision

**uv.** Pin the Python version in `.python-version` (3.12 — supported by PyTorch 2.4-2.6 per the PyTorch release compatibility matrix, see ADR-0006), declare dependencies in `pyproject.toml` with dependency groups, commit `uv.lock`, and use `uv sync` in dev, CI, and deployment. The worker's PyTorch/CUDA pin (ADR-0006) is a separate locked extra so the backend environment stays light.

## Consequences

- Easier: reproducible environments everywhere; one command to recreate the dev environment; clean separation of backend vs worker heavy deps.
- Harder: everyone uses uv; CI must run offline-capable installs from the lockfile (mirror configuration per hardware.md section C).
- Must verify later: `uv sync` works against the configured package mirror on the target server (Phase 1 setup).

# ADR-0006: PyTorch / CUDA Versions for Pascal (GTX 1080 Ti, sm_61)

- Status: Proposed
- Date: 2026-10-05 (rewritten with current release data; supersedes the 2026-10-05 initial draft's version claims)

## Context

The initial GPUs are GTX 1080 Ti (Pascal, compute capability 6.1, 11 GB, no tensor cores, no bf16 — AGENTS.md). The worker runs PyTorch-based inference (ComfyUI/diffusers engines, spec sections 41-42). AGENTS.md requires verifying PyTorch/CUDA compatibility with Pascal before choosing versions and recording it in this ADR. Every claim below is cited to an official source; anything unconfirmable is marked **needs verification** and tracked in `docs/verification-checklist.md`.

## Established facts (cited)

1. **Currently supported PyTorch versions: 2.7 through 2.14.** The official release compatibility matrix lists stable CUDA builds for 2.7, 2.8, 2.9, 2.10, 2.11, 2.12, 2.13, and 2.14. The latest stable release is **2.14.0 (2026-09-02)**; 2.15 is scheduled for 2026-10-28. [Sources: PyTorch RELEASE.md support matrix](https://github.com/pytorch/pytorch/blob/main/RELEASE.md), [PyTorch 2.14 release blog](https://pytorch.org/blog/pytorch-2-14-release-blog/), [Wikipedia stable-release table](https://en.wikipedia.org/wiki/PyTorch)]
2. **CUDA builds that still include Pascal (sm_60/sm_61): cu118 and cu126 only.**
   - cu118: stable builds for PyTorch 2.7 and earlier (2.7 stable CUDA: 11.8, 12.6). [Source: RELEASE.md matrix]
   - cu126: the RELEASE.md architecture table states for releases 2.12-2.14, "CUDA 12.6.3: Maxwell(5.0), **Pascal(6.0)**, Volta(7.0), Turing(7.5), Ampere(8.0, 8.6), Hopper(9.0)". The PyTorch dev-discuss policy announcement confirms cu126 is the retained line for Pascal: "If you need support for these architectures, please utilize CUDA 12.6 instead." [Sources: RELEASE.md](https://github.com/pytorch/pytorch/blob/main/RELEASE.md), [PyTorch dev-discuss](https://dev-discuss.pytorch.org/t/cuda-toolkit-version-and-architecture-support-update-maxwell-and-pascal-architecture-support-removed-in-cuda-12-8-and-12-9-builds/3128)
   - **cu128/cu129: Pascal dropped starting with PyTorch 2.8.** Official release notes: "support for sm50 - sm60 architectures with CUDA 12.8 and 12.9 has been dropped for the 2.8.0 release." [Sources: PyTorch GitHub releases](https://github.com/pytorch/pytorch/releases), [dev-discuss](https://dev-discuss.pytorch.org/t/cuda-toolkit-version-and-architecture-support-update-maxwell-and-pascal-architecture-support-removed-in-cuda-12-8-and-12-9-builds/3128)
   - **cu130/cu132: no Pascal.** These are stable builds for 2.11-2.14; the 2.13 release notes confirm the CUDA 12.8/12.9 build variants were removed entirely for 2.13+, leaving 12.6 as the only Pascal-capable line. [Sources: RELEASE.md](https://github.com/pytorch/pytorch/blob/main/RELEASE.md), [PyTorch 2.13 release blog](https://pytorch.org/blog/pytorch-2-13-release-blog/)
3. **sm_60 cubins run on sm_61 hardware.** NVIDIA's Pascal Compatibility Guide: a cubin targeting compute capability X.Y is supported on all compute capability X.Z devices (same major version). PyTorch's own capability check implements the same rule ("NVIDIA GPU compute architectures are backward compatible within major version"). [Sources: NVIDIA Pascal Compatibility Guide (CUDA 12.6 archive)](https://docs.nvidia.com/cuda/archive/12.6.1/pascal-compatibility-guide/index.html), [PyTorch torch/cuda source](https://github.com/pytorch/pytorch/blob/main/torch/cuda/__init__.py)
4. **Current ComfyUI requires PyTorch >= 2.7.** Official system requirements: "PyTorch 2.7 and above is supported, but using a newer version is strongly recommended. A cu130 or above version of PyTorch is required on Nvidia 20 series and above." ComfyUI's `requirements.txt` leaves `torch` unpinned. [Sources: ComfyUI system requirements](https://docs.comfy.org/installation/system_requirements), [ComfyUI requirements.txt](https://github.com/Comfy-Org/ComfyUI/blob/main/requirements.txt)]
5. **bf16 is not available on Pascal.** The PyTorch CUDA backend supports bfloat16 on Ampere or newer GPUs; on unsupported devices `torch.cuda.is_bf16_supported()` returns False and autocast raises "Current CUDA Device does not support bfloat16. Please switch dtype to float16." [Sources: PyTorch AMP documentation](https://docs.pytorch.org/docs/stable/amp.html), [PyTorch forum confirmation quoting the docs](https://discuss.pytorch.org/t/question-about-bfloat16-operations-in-amp-and-cuda/206078)
6. **Pascal has no tensor cores**, so TF32 and bf16 acceleration are unavailable; fp16 runs on CUDA cores. [Source: CUDA Programming Guide, compute-capability feature table](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/compute-capabilities.html)
7. **Driver minimums:** cu126 requires Linux driver >= 560.28.03 (GA; >= 560.35.05 for 12.6 Update 3); cu118 requires Linux driver >= 520.61.05. [Source: CUDA 12.6 release notes](https://docs.nvidia.com/cuda/archive/12.6.0/cuda-toolkit-release-notes/index.html), [CUDA 11.8 driver table](https://docs.nvidia.com/cuda/archive/12.6.0/cuda-toolkit-release-notes/index.html)]
8. **Python:** PyTorch 2.7-2.14 all support Python 3.10+; 2.14 requires >= 3.10. Python 3.12 is supported across the whole viable range. [Source: RELEASE.md](https://github.com/pytorch/pytorch/blob/main/RELEASE.md)

## Viable combinations for Pascal + current ComfyUI

| Combination | Pascal support | ComfyUI >= 2.7 | Driver (Linux) | Verdict |
|-------------|---------------|----------------|----------------|---------|
| PyTorch 2.7.x + cu118 | Yes (fact 2) | Yes (minimum) | >= 520.61.05 | Viable |
| PyTorch 2.7.x + cu126 | Yes (facts 2-3) | Yes | >= 560.28.03 | **Recommended** |
| PyTorch 2.8.x - 2.14.x + cu126 | Yes (facts 2-3) | Yes | >= 560.28.03 | Viable (newer features) |
| Any 2.8+ with cu128/cu129/cu130/cu132 | **No** (fact 2) | — | — | Rejected for Pascal |
| Any 2.6 or older + any CUDA | Yes | **No** — below ComfyUI minimum (fact 4) | — | Rejected |
| bf16 anywhere | — | — | — | Impossible on Pascal (fact 5) |

## Options considered

1. **PyTorch 2.7.x + cu126 (recommended)** — the minimum PyTorch line that current ComfyUI supports, on the CUDA line that retains Pascal longest.
   - Pros: satisfies ComfyUI's >= 2.7 requirement with the widest margin; cu126 is the Pascal-retained build across all PyTorch versions (fact 2); driver requirement (560.28.03) is modest.
   - Cons: not the newest PyTorch; some newer ComfyUI optimizations may prefer newer torch (ComfyUI docs note "some features and optimizations might only work on newer versions").

# ADR-0007: Pluggable GPU Backend (Real NVML + Mock)

- Status: Proposed
- Date: 2026-10-05

## Context

AGENTS.md requires the worker to support a pluggable GPU-discovery/execution backend: a real one (NVML / nvidia-smi) and a MOCK one that simulates N GPUs with configurable VRAM, utilization, failures, and OOM. All scheduler/queue/worker tests must run against the mock in CI. The dev machine has no GPU (hardware.md section A). Spec sections 5-8 require automatic GPU discovery, a dynamic capability system, and GPU lifecycle states — all without hard-coding GPU names or counts.

## Options considered

1. **Interface + two adapters (NVML real, in-process mock)**
   - A `GpuBackend` port defines: `list_devices()`, `get_metrics(device_id)`, `get_capabilities(device_id)`, `run_probe(device_id, probe)`, `allocate/free`, `execute(job)`.
   - `NvmlGpuBackend` wraps NVML (via `pynvml` or `nvidia-smi` parsing) on real workers.
   - `MockGpuBackend` simulates N GPUs with configurable VRAM, utilization, temperature, power, injected failures, and OOM; selected by config/env var in dev and CI.
   - Pros: zero GPU needed for the entire test suite; failure/OOM paths are testable deterministically (spec section 93); capability decisions stay data-driven (AGENTS.md); swapping backends is config, not code.
   - Cons: the mock must be kept honest (modeled on real NVML semantics); two code paths to maintain.

2. **Real NVML only, tests against recorded fixtures**
   - Pros: one code path.
   - Cons: cannot test OOM/failure injection deterministically; CI still needs a GPU or heavy faking; violates the AGENTS.md mock requirement. Rejected.

3. **External GPU simulator sidecar**
   - Pros: none over option 1.
   - Cons: extra process, extra ops. Rejected.

## Decision

**Interface + two adapters** (option 1). The backend is selected by configuration (`GPU_BACKEND=auto|nvml|mock`), never by GPU-name if-statements (AGENTS.md). `auto` uses NVML when available, else mock. The mock is a first-class component with its own tests and is the mandatory backend for CI scheduler/queue/worker tests. Capability determination (spec section 6) consumes backend-reported data (compute capability, VRAM, driver, probe results) through a registry of capability rules — no hardware names in business logic.

## Consequences

- Easier: full test coverage without GPUs; deterministic failure injection; dev and CI run identical code paths.
- Harder: the mock must mirror NVML semantics closely enough that behavior differences surface only in real-GPU verification (V-004, V-005).
- Must verify later: V-004 (real NVML backend matches nvidia-smi), V-005 (metrics parity).

# ADR-0008: Database

- Status: Proposed
- Date: 2026-10-05

## Context

Spec section 62 requires a production-grade relational database, PostgreSQL preferred unless a strong technical reason exists. The schema must be normalized, extensible, indexed, migration-based, and version-controlled (spec section 62). Spec section 63 lists the core entities. ADR-0002 selects a Postgres-backed queue for Phase 1-3, which assumes Postgres. The dev stack must fit in ~4 GiB RAM.

## Options considered

1. **PostgreSQL**
   - Pros: spec-preferred; required by the Phase 1-3 queue choice (ADR-0002); excellent JSON support for extensible metadata; mature migrations (Alembic); strong ecosystem; runs comfortably in the RAM budget.
   - Cons: none material at this scale.

2. **MySQL / MariaDB**
   - Pros: familiar.
   - Cons: weaker JSON/extensibility story; no advantage over Postgres for this workload; not spec-preferred.

3. **SQLite**
   - Pros: zero infra.
   - Cons: not production-grade for concurrent writers (spec section 62); rejected.

## Decision

**PostgreSQL** (latest stable major available on the target OS). Migrations via Alembic, version-controlled in the repository. Connection access only through the persistence layer (spec section 66 separation).

## Consequences

- Easier: one store for business data and the Phase 1-3 queue; single backup story.
- Harder: none material.
- Must verify later: Postgres version availability on the target server (V-001).

./docs/design/08-scheduler-architecture.md:13:## Allocation ownership (single owner: the scheduler)
./docs/design/08-scheduler-architecture.md:15:**The scheduler is the sole owner of GPU allocation.** The queue orders and claims jobs; the scheduler decides and reserves GPUs; the worker only executes jobs already reserved for its GPUs (see `18-worker-protocol.md`). No other component may transition a GPU's lifecycle state.
./docs/design/08-scheduler-architecture.md:19:1. **Filter** — candidate GPUs must: be `AVAILABLE` (spec section 7 lifecycle), on a `HEALTHY` node, satisfy the job's capability requirements, have sufficient free VRAM (model requirement + safety margin), and match any user pinning (GPU/node/GPU set).
./docs/design/08-scheduler-architecture.md:21:3. **Reserve** — atomically, in one DB transaction (Phase 1-3): GPU `AVAILABLE → RESERVED` and job `QUEUED → RESERVED`, recording the allocation (node, GPU, policy, scores). Double allocation is impossible by construction.
./docs/design/08-scheduler-architecture.md:22:4. **Dispatch** — the job becomes claimable by the worker on the reserved node; the claim carries the reserved GPU id.
./docs/design/08-scheduler-architecture.md:23:5. **Activate** — when the worker reports the job as STARTING, the scheduler transitions the GPU `RESERVED → BUSY` in the same transaction as the job `RESERVED → STARTING`. (The worker's report is the trigger; the scheduler remains the owner of the transition.)
./docs/design/08-scheduler-architecture.md:24:6. **Release** — on completion/failure/cancellation, `BUSY → AVAILABLE` (or `UNHEALTHY` if the GPU reported errors). If a job never starts (worker lost, lease expired), the reservation is released `RESERVED → AVAILABLE` and the job returns to `QUEUED`.
./docs/design/08-scheduler-architecture.md:31:| FASTEST | Prefer the GPU with the highest expected throughput for the model (from probe/benchmark data) |
./docs/design/08-scheduler-architecture.md:36:| ROUND_ROBIN | Cycle across compatible GPUs |
./docs/design/08-scheduler-architecture.md:37:| MANUAL | User-pinned GPU/node/GPU set only |
./docs/design/08-scheduler-architecture.md:39:Policies are pluggable: a policy is a scoring function over the candidate set. New policies register without modifying the scheduler core (spec section 12 extensibility).
./docs/design/08-scheduler-architecture.md:43:`LOW < NORMAL < HIGH < URGENT`. The queue claims highest-priority-oldest first; preemption is **not** performed (a running job is never evicted) — priority affects ordering only.
./docs/design/08-scheduler-architecture.md:45:## Multi-GPU jobs (spec section 8)
./docs/design/08-scheduler-architecture.md:47:Only when the model version + engine adapter declare multi-GPU support: the scheduler allocates the requested GPU set atomically (all-or-nothing) and validates the set against capabilities.

./docs/design/18-worker-protocol.md:57:## 4. Job delivery — pull model with leases
./docs/design/18-worker-protocol.md:59:**Decision: workers pull jobs; the control plane never pushes execution commands.**
./docs/design/18-worker-protocol.md:61:- The scheduler reserves a GPU for the job (see `08-scheduler-architecture.md` — the scheduler is the sole allocation owner) and the job becomes claimable by a worker on the reserved node.
./docs/design/18-worker-protocol.md:62:- The worker claims via **`POST /api/v1/workers/{id}/jobs/claim`** (POST, not GET — claiming has side effects: it creates a claim/lease record and starts the lease timer). Long-poll or short interval.
./docs/design/18-worker-protocol.md:63:- The claim response carries the job **and the reserved GPU id**. The worker never chooses a GPU; it re-validates capabilities/VRAM against the reserved GPU before starting (safety net, not the allocation mechanism).
./docs/design/18-worker-protocol.md:64:- Pull was chosen over push because: NAT/firewall-friendly (workers may sit behind routers), naturally balanced (workers claim when ready), simpler recovery (a crashed worker's jobs are simply re-allocated after heartbeat loss), and it keeps the control plane stateless w.r.t. connections.
./docs/design/18-worker-protocol.md:66:### Claim lease (visibility timeout)
./docs/design/18-worker-protocol.md:68:- Every claim creates a **lease**: `claim_id`, `job_id`, `worker_id`, `expires_at` (default 60 s, configurable).
./docs/design/18-worker-protocol.md:69:- While a lease is valid, the job is invisible to other workers' claims (visibility timeout pattern).
./docs/design/18-worker-protocol.md:70:- **Lease renewal:** the worker's heartbeat (section 3) includes its active `claim_id`s; each heartbeat renews those leases (extending `expires_at`). A dedicated `POST /api/v1/workers/{id}/claims/{claim_id}/renew` exists for renewal between heartbeats.
./docs/design/18-worker-protocol.md:71:- **Lease expiry:** if `expires_at` passes without renewal (worker crashed, hung, or partitioned):
./docs/design/18-worker-protocol.md:72:  1. The claim is released; the job returns to `QUEUED` (visible immediately, or after a short delay if it had already started).
./docs/design/18-worker-protocol.md:73:  2. A new `job_attempts` row records the lost attempt with error `worker_lost` (retryable).
./docs/design/18-worker-protocol.md:74:  3. The GPU reservation is released (`RESERVED → AVAILABLE`, or `BUSY → AVAILABLE`/`UNHEALTHY` if the job had started) and the scheduler re-selects a GPU per the retry policy (spec section 14).
./docs/design/18-worker-protocol.md:75:  4. If the "worker" was actually alive but slow (e.g. model load exceeded the lease), the next claim creates a fresh attempt — the old attempt's partial progress is discarded, keeping execution idempotent-at-checkpoint.
